01 Executive summary and readiness verdict

Verdict: a convincing UI prototype, not yet a product. Reset first, then build.

The repository is a Lovable-generated TanStack Start front end with five routes, two hard-coded data modules and a handful of inline rules. Everything runs in the visitor's browser. There is no API, no database, no login, no test, no CI and no server-side rule of any kind. Submitting a reservation flips a React flag; approving one edits an in-memory array that a page refresh discards.

The README, landing page and reservation form all describe capabilities (conflict detection, automatic notifications to IT, custodial and security, analytics, AWS deployment) that do not exist in the code. The team already knows this: DEBT_AND_RISK.md (September 17) and the backlog notes (September 23) are accurate and candid. This report confirms them against the code, adds what they missed, and turns them into a sequenced plan.

The most important finding is not technical. The team has produced excellent planning artifacts, but the board shows three tickets in progress or in review that have no branch or pull request behind them. Senior Project II starts with a well-groomed backlog and an unbuilt foundation.

03 Current system architecture

The application is a single front-end bundle. TanStack Start renders a server-side HTML shell and then hydrates in the browser, but the project contains no server code of its own: no server functions, no API routes, no environment bindings. Every route imports its data from two static TypeScript modules compiled into the bundle, applies rules inline during render, and keeps any edits in component state.

3.3 Data flow: life of a request today

  1. A visitor opens /reserve. The route component builds FormState in useState and recomputes recommendRooms(attendance) and an issues[] array on every keystroke.
  2. Validation errors disable the submit button. Warnings (after-hours, external guests with 50 or more attendees, food) are shown but nothing records them.
  3. On submit, the handler calls setSubmitted(true). No object is built, nothing is posted, no ID is generated. The success panel promises “status updates as it moves through approval”.
  4. The “View My Requests” link opens /dashboard, which renders the same five hard-coded MOCK_REQUESTS for every visitor. The request just “submitted” is not among them.
  5. On /admin, approve and reject call setStatus(), which maps over a useState copy of MOCK_REQUESTS. A refresh restores the original five rows. No feedback, actor or timestamp is captured.
  6. No notification, email, webhook or log is produced at any step, although the landing page, the form's tip box and the README all say otherwise.

6.3 Working agreements for Senior Project II

  • One metric: merged PRs per week, reviewed at every standup. Target two in Sprint 0, three or more afterwards.
  • Definition of Ready: dependencies Done or stubbed; owner; size; milestone; acceptance criteria unchanged from the body.
  • Definition of Done: PR says Closes #n; CI green; one reviewer who is not the author; acceptance checkboxes ticked; README updated if a claim changes.
  • No status without a branch. “In progress” requires a branch named <issue>-short-title; “In review” requires an open PR.
  • Verify before trust: AI-generated code (Lovable, Cursor, Copilot) is a draft until a test proves it. Risk, auth and persistence changes get a human walkthrough in review.
  • Ask the client early: policy thresholds, room inventory and notification preferences are requested in Sprint 0, not when the ticket starts.
What success looks like on December 1, 2026. A student logs in, reserves a free room for a real date, and sees the request pending. An admin logs in, sees the risk flags, approves with a note, and the student sees it approved after a refresh. All of it on a URL the team controls, with a Playwright test that proves it on every pull request. Everything after that is decision support on top of a real system.
