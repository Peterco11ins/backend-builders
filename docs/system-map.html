CEA Reserve System Map

A high-level view of the event space reservation system: the final architecture the application is being built toward, what the repository implements today, what the fifteen open GitHub issues add, and the order they have to land in.

1. Architectural diagram

The final architecture baseline of the application: the system as it is meant to run once the backlog is delivered. Users sign in through Howard SSO, the existing frontend talks to a reservation API over HTTPS, every rule runs once in a shared domain module on the server, and approvals persist and fan out to the service teams.

2. Current implementation: layered view of the repository

A layered view of the repository at commit f317c48. The red dashed box is the trust boundary: every layer inside it runs in the visitor's browser, so nothing the client checks can be relied on. The bottom rows show how the app is built and served, and the six components the README describes that do not exist in the code.

3. Target architecture: today versus target

The left side is what runs now. Every route reads from two static TypeScript modules and holds edits in React state, so a refresh discards each submission and approval. The right side is the layered system the backlog describes, with the issue number that delivers each part.

4. Life of a reservation request

This is the path a request takes through the app, with the rules the code applies at each step. The client-side checks and room suggestions work today. Persisting the submission and notifying staff are planned.

7. What the audit flags

Open admin surface

  • Anyone can approve or reject on /admin.
  • Fixed by #14, which needs #13 for server-side sessions.

Rules live in the UI

  • Capacity and after-hours checks sit inline in the reserve page.
  • Risk score is display only and never enforced.

Docs ahead of code

  • README promises an API, conflict detection, notifications, and AWS.
  • Package is still named tanstack_start_ts, with both Bun and npm lockfiles.

Zero tests

  • No runner, no test script, no CI workflow.
  • #15 is small, has no dependencies, and unblocks the definition of done for every other ticket.
